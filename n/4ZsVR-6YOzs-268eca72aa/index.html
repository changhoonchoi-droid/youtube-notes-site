How Salesforce uses Claude Code

Claude · 게시 2026-11-06

▶ 원본 영상 보기

한눈에 보기

  • Salesforce는 Claude Code로 수십 년 된 코드의 API를 몇 주~몇 달 만에 정리해 전 클라우드 플랫폼의 API 커버리지를 80~90%까지 끌어올렸다(원래 6개월~1년 예상).
  • 스탠퍼드 연구진과 만든 '효과적인 출력(effective output)' 점수로 ROI를 측정했고, 그 결과 출력량이 약 두 배가 됐다.
  • 코드량은 두 배로 늘었지만 코드당 버그 수는 오히려 줄었다 — 표준화된 SDLC·티켓·PR 데이터와 견제 장치 덕분이라고 설명한다.
  • 엔지니어를 단순 프롬프트에서 자율 에이전트 단계(P3·P4)로 옮기는 '에이전트 성숙도 곡선'과, 스킬을 평가해 공유하는 마켓플레이스가 확산의 핵심이었다.
  • "검증 없는 자율성은 자신감 쇼(confidence theater)"라며, 에이전트에게 객관적 기준에 따른 증거를 요구하고 작업에 맞는 모델을 고르라고 조언한다.

이런 분께 도움이 됩니다

  • 조직에 AI 코딩 도구를 도입하고 ROI를 어떻게 잴지 고민하는 엔지니어링 리더·CTO.
  • 에이전트에게 얼마나 큰 일을 맡기고 어떻게 검증할지 감을 잡고 싶은 개발자.

핵심 내용

도입 성과: 헤드리스화와 코드 이해

  • 수십 년 된 Salesforce 코드를 모든 애플리케이션이 API를 갖는 '헤드리스(headless)' 구조로 만드는 작업을 Claude Code로 몇 주~몇 달 만에 끝냈다. 원래는 페이지마다 API를 확인하고 빈틈을 찾느라 6개월~1년이 걸릴 일이었다. (0:48)
    • 팀 간 회의 없이 모든 클라우드 플랫폼의 API 커버리지 80~90%를 달성했다.
    • 새 코드가 아니라 기존 코드를 활용해 이뤘다는 점을 놀라운 일로 꼽았다.
  • 한 아키텍트의 말: 남의 코드를 이해하려고 3~4개 팀과 소통하며 며칠씩 쓰던 회의가 사라진 것이 큰 변화였다. (6:14)
  • 인시던트 대응: 에이전트가 원인과 담당 팀을 찾아 Slack에 근거(POC)를 공유하고 이관한다. 예전에는 약 9개 팀이 동시에 호출받던 상황이 정리됐다. (7:01)

💡 코드를 이해하는 데 드는 사람 간 조율 비용이 가장 먼저 줄었다.

ROI 측정: '효과적인 출력'

  • 코드 줄 수나 주석 양으로는 가치를 판단할 수 없어서, 스탠퍼드 연구진과 코드의 품질·효율을 점수화하는 '효과적인 출력' 지표를 만들었다. (1:37)
    • 단순 수정·주석 추가는 낮은 점수, 로직 변경·새 기능은 높은 점수.
    • 이 지표로 AI 도입 전후 변화와 '효과적인 출력당 비용'을 볼 수 있다.
  • 결과: 효과적인 출력이 두 배로 늘었다고 한다. (2:23)
  • 비코딩 직무(영업·지원 등)도 기능별 지표(계약 성사 수, 처리 사례 수 등)를 정해 도입 전후를 비교한다. 차이가 없으면 사용법 문제인지 도구가 안 맞는 건지 원인을 따진다. (2:45)

에이전트 성숙도 곡선

🔁 에이전트 성숙도 단계
  1. 간단한 지시
  2. 기준·계획 수립
  3. 팀·병렬 작업
  4. 자율·자동화
  1. 1간단한 지시

    "가서 해줘" 식 명령. 간단한 작업만 처리되고, 좋은 결과의 기준이 없어 큰 작업에서 막힌다. (4:17)

  2. 2기준·계획 수립

    무엇을 알아야 하고 무엇을 고려해야 하는지, 좋은 결과와 나쁜 결과를 정의하고 포괄적인 계획을 세운다.

  3. 3팀·병렬 작업

    서브에이전트, 작업 분해, 작업 트리 관리, 병렬 처리를 활용한다.

  4. 4자율·자동화

    에이전트들이 SDLC 전반의 워크플로우를 관리한다. 예: CI/CD에서 테스트 실패 시 한 에이전트가 원인을 고치고, 다른 에이전트가 코드 리뷰 후 병합한다. (5:04)

  • 처음엔 기본 작업에만 쓰던 엔지니어 다수가 한두 달 만에 P3·P4 단계로 올라갔고, 지금은 수천 명이 자율 모드로 일한다. (3:55)
  • 가장 큰 과제는 역량 강화(enablement)였다. P3·P4 도달이 제로섬이 아니라는 점을 설명하는 것이 중요했다.

확산 방법

  • 실제 데이터와 영감으로 접근: 직원들이 자기 작업 방식을 라이브로 시연하고, 각 클라우드 팀이 몇 달 걸릴 일을 몇 주 만에 해낸 사례를 공유했다. (5:50)
  • 실제 출시 제품을 Dreamforce(Reinforce로 자막 표기) 행사에서 발표해 "정말 효과가 있다"는 점을 보여 줬다.
  • 혁신은 상향식으로 일어나게 하고, 효과가 보이면 확장을 돕는다. (8:52)

스킬 마켓플레이스와 평가

  • 팀들이 만든 스킬을 공유하려는 아이디어에서 시작했다. 온라인 평가로 세션을 다시 보고, Claude가 스킬 개선(토큰 효율, 더 빠른 결론)을 제안하게 한다. (7:21)
  • 공유되는 스킬이 실제 결과에 가치를 주는지 보여 줄 수 있고, 전체 엔지니어링 수준부터 소규모 스크럼 팀까지 계층 구조로 쓴다. (8:07)
  • 수천 개 리포지토리에서 버그 수정을 대중화하려면, 처음 보는 코드베이스를 다루고 품질 높은 PR을 만드는 워크플로우가 필요하다.

품질 가드레일

  • 최근 몇 달간 코드량이 거의 두 배가 됐지만 코드당 버그 수는 평균적으로 줄었다. (9:39)
  • 이유: 사람이 하는 일에 대한 견제와 균형, 기존·신규 품질 메커니즘이 제대로 작동했기 때문.
  • 측정 가능한 이유: 모두 표준 SDLC를 따르고 티켓 라벨링이 일관되며 모든 데이터가 PR과 연결돼 있다. (10:27)
  • 스킬 품질은 과학적으로 평가한다 — 사용자가 무엇을 이루려는지 묻고, 공유 후 다른 개발자가 실제 가치를 얻는지 확인한다. (9:16)

새 모델 검증: 벤치마크 재생

  • 벤치마크를 만들어 두고, 새 모델을 PDLC 전반의 단·장기 작업에 시뮬레이션해 비용·성능(더 나은가, 나쁜가)을 비교한다. (10:49)
  • 새 기능인 'Fail to Failure' 테스트는 장기 작업 중 모델이 계속 실패하던 지점을 찾아, 새 모델이 통과하면 채택 근거로 삼는다. (11:12)

검증 없는 자율성은 '자신감 쇼'

  • 객관적 기준으로 에이전트 작업을 측정한다. 좋은 결과와 나쁜 결과(음성 테스트 케이스: 기존 스키마를 건드리지 않았는지, 새 스키마를 만들라 했는데 기존 엔티티에 필드를 추가하지 않았는지)를 정의한다. (11:37)
  • 에이전트에게 "스스로 검토해"라고 하지 않고 "품질·실패 특징을 찾았는가, 증거를 보여 달라"고 요구한다. 특징을 매트릭스로 만들어 오게 하고, 부족하면 되돌려 보낸다. (12:22)

💡 자기 검토가 아니라 증거 제출을 요구한다.

작업 크기와 모델 선택

  • 스토리 포인트가 클수록 좋다. 아주 작은 일은 에이전트 투입 노력이 아깝고, 큰 기능을 통째로 맡기면 모델·도구가 스스로 독립 작업으로 분해한다. 몇 분짜리 일은 빠른 상호작용 세션으로 취급한다. (12:44)
  • 사람이 하던 작업 분해를 에이전트 팀이 대신할 수 있고, 사전 계획이 좋을수록 결과가 좋다. (13:32)
  • 가장 큰 실수는 작업에 맞는 모델·가격·ROI를 고르는 것. 단순한 파일 생성에는 고성능 모델이 필요 없고, 작업의 길이·복잡도를 함께 본다. (13:52)
  • 사례: 원인을 찾지 못한 제품 버그를 Opus가 디버그→수정→컴파일을 반복하며 24시간 만에 찾아 수정안을 냈고, 중요한 비즈니스 소프트웨어이므로 검증 과정을 거쳤다.

기억할 숫자·인용

  • API 커버리지 80~90%, 6개월~1년 → 몇 주~몇 달
  • 효과적인 출력 약 2배, 코드량 약 2배인데 코드당 버그는 감소
  • "검증 없는 자율성은 자신감 쇼에 불과하다" (11:37)
  • 조언: "과감해지세요", 참여 시스템에서 주체성(agency) 시스템으로의 전환 (15:13)

생각해볼 점

  • 영상 속 수치는 Salesforce 내부 발표이며 외부 검증 자료는 없다. '효과적인 출력' 점수의 구체적 산식도 공개되지 않았다.
  • 표준화된 티켓·PR 데이터가 이미 있는 조직이라 가능한 측정일 수 있어, 데이터가 부실한 조직은 그대로 따라 하기 어렵다.
  • 자막이 자동 생성이라 일부 용어(예: Dreamforce/Reinforce, Claudeforce, '우화적/소네트적' 문제 = Opus/Sonnet 비유로 추정)는 불분명하다.

바로 해볼 일

  • 우리 팀의 AI 코딩 성과를 줄 수가 아니라 '변경의 무게(로직·기능 vs 단순 수정)'로 가늠할 지표를 정해 본다.
  • 에이전트에게 맡기는 다음 작업에 "좋은 결과/나쁜 결과 기준"과 "증거 제출"을 프롬프트에 넣어 본다.
  • 반복되는 작업 흐름 하나를 스킬로 정리해 팀에 공유해 본다.
