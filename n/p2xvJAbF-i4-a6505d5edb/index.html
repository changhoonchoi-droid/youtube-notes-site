Building the Claude API for the Frontier

한눈에 보기

  • Messages API는 시스템·사용자 턴과 도구 호출로 이루어진 Claude API의 기본 구조이고, effort(노력 수준) 같은 조절 장치(knob)로 동작을 크게 바꿀 수 있다.
  • 새 기능은 연구팀의 발견과 고객 요청이 양방향으로 오가며 정해지고, 품질 기준(eval)을 넘은 것만 출시된다.
  • 모델이 바뀔 때는 기능을 추가하는 건 쉽지만 없애는 건 어렵기 때문에, 한동안 옛 방식으로 되돌릴 수 있게 두었다가 단계적으로 폐지한다.
  • 비용 절감의 첫 번째 수단은 프롬프트 캐싱(캐시 적중률 90%가 목표)이고, 토큰당 가격보다 "토큰당 지능"과 작업당 비용을 봐야 한다.
  • Mythos와 Fable은 같은 모델 가중치이며, 분류기(classifier)와 인증 절차로 쓸 수 있는 범위만 다르다.

이런 분께 도움이 됩니다

  • Claude API로 에이전트나 앱을 만들면서 비용과 모델 업그레이드 전략을 고민하는 개발자.
  • 새 모델이 나올 때마다 하네스(harness, 모델을 감싸는 프롬프트·도구·루프 구성)를 어떻게 재점검할지 알고 싶은 분.

핵심 내용

Messages API와 조절 장치

  • Messages API는 Claude API의 핵심(cornerstone)이다. 시스템 턴, 사용자 턴, 중간의 도구 호출이라는 업계 표준 구조 위에서 원하는 것을 만들 수 있다. (0:24)
  • 그 위에 동작을 바꾸는 조절 장치가 얹혀 있다. 같은 모델도 effort를 높게 또는 낮게 주면 하이브리드 모델을 고른 것처럼 느낌이 달라진다.
  • 연구팀과 같은 공간에서 일하며 Claude가 가장 잘하는 방식을 기본값으로 넣었다. 문서의 가장 기본적인 요청을 복사해 써도 최상의 기본 경험을 얻는다.

    💡 프롬프트로 유도하는 것보다 API 조절 장치가 훨씬 깊은 수준의 맞춤을 가능하게 한다.

기능이 출시되는 과정

  • 연구팀 → API 방향: 연구자가 Claude의 새로운 강점을 발견하면 기능이 된다. 예: 컴퓨터 사용 능력이 좋아진 것이 computer use 도구가 됐다. (1:53)
  • 고객 → API 방향: 고객 요청이 연구팀의 학습 요청으로 바뀌고, 이미 나온 모델이 아니라 다음 모델에 반영된다.
  • 출시 전 첫 단계는 Claude가 그 기능을 얼마나 잘 쓰는지 평가(eval)하는 것이다. 고객에게도 각자 용도가 있으므로 자체 eval을 돌리라고 권한다. (4:05)
  • 대표 사례 두 가지: 대화 중 effort 변경, 대화 중 시스템 프롬프트 변경. 예전에는 바꾸면 프롬프트 캐시가 깨져 사실상 쓸 수 없었다. (3:00)
    • 높은 effort로 돌던 에이전트가 다음 요청이 쉬운 걸 알아도, effort를 낮추면 캐시가 깨져 비용 절감 목적이 무너졌다.
    • 대화 중 effort 변경(베타)은 이 문제를 해결한다.

모델 버전 관리와 마이그레이션

  • 모델 문자열이 곧 버전 역할을 하고, API 버전·프롬프트 안정성과 얽혀 있다. 모델이 지능의 최전선에 있어 사용자가 변경을 감수할 가치가 크다.
  • 기능 추가는 불만이 없지만, 누군가 많이 의존하는 기능을 폐지하는 것이 어렵다.
  • 사례: 기존 확장 사고(extended thinking)에서 적응형 사고(adaptive thinking)로 전환. eval에서 이미 더 좋았지만 한동안 옛 방식으로 되돌릴 수 있게 두었다. 베타 헤더 등으로도 롤백할 수 있다. (6:33)
  • 결국 모델이 옛 방식으로 더 이상 학습되지 않으면 하드 폐지가 필요하다. 아무 동작도 안 하는 API를 남기는 것이 더 해롭기 때문이다. 그래도 모델 한두 세대는 천천히 이전할 시간을 준다.

    💡 강제 폐지는 하네스에서 이제 불필요해진 부분을 다시 점검하게 만드는 계기다.

  • 모델이 10배 똑똑해지면 하네스 자체가 한계가 될 수 있으므로, 모델이 바뀔 때마다 앱·루프·설정 전체를 주기적으로 재평가하라고 권한다. (8:02)

비용 관리

  • 프롬프트 캐싱이 가장 큰 비용 수단이다. 캐싱을 최적화하지 않은 고객에게 가장 먼저 하는 권고다. (8:35)
    • 에이전트 대화처럼 두 번째 요청이 첫 요청에 내용만 덧붙이는 구조일 때, 이미 처리한 블록을 캐시한다.
    • 영업팀도 "캐시율을 90%까지 올릴 수 있나?"를 먼저 묻는다. 꿈의 수치로 통한다.
  • 토큰당 비용에는 "토큰당 지능"이라는 차원이 필요하다. 고지능 모델(Fable)과 Haiku는 같은 결과를 내는 데 쓰는 토큰 수가 크게 다르다. (9:32)
    • 일부 기능은 토큰 단가를 바꾸지 않고 사용 토큰 수를 바꾼다.
    • Haiku·Sonnet을 쓰는 사용자가 상위 모델로 바꾸면 더 좋은 결과를 얻는 경우가 있다.
    • 반대로 모델이 전반적으로 좋아지면, 예전엔 Fable 5만 풀던 작업을 Opus 5가 풀 수도 있다.
    • 비교 기준은 결국 eval이다.

Mythos와 Fable, 안전장치

  • 모든 API 모델은 오용을 막는 분류기를 거친다. 과학 연구 등 선한 사용을 위해 접근은 열되, 악용 우려는 균형을 잡는다. (12:37)
  • Mythos와 Fable은 같은 모델 가중치이며, 분류기에 따라 할 수 있는 범위만 다르다.
    • Mythos: 사이버 분야 등에서 올바른 사람에게 접근을 주기 위한 인증 절차(KYC, 영상 설명상 Cyber Verification Program)를 거친다.
    • Fable: 그 절차를 거치지 않은 누구나 쓸 수 있다.
  • 증류(distillation, 강한 모델의 출력으로 다른 모델을 학습시키는 것) 방지도 안전의 한 축이다. 안전장치 없는 모델이 퍼지는 것은 위험하며, 최근 사고(thinking) 보호 변경도 이 때문이라고 문서로 밝혔다. (13:21)
  • 공개된 한 가지 변경 뒤에는 내부 실험 10가지 정도가 있고, 데이터 기반으로 오랜 시간 결정한다. 모델이 너무 잘해 eval을 더 어렵게 만들어야 하는 "eval 포화"도 겪는다. (14:06)

앞으로의 방향

  • 가장 중요한 것은 모델 지능이다. 새 모델이 나오면 기준에 못 미쳐 출시하지 않았던 기능들을 eval로 다시 돌려, 기준을 넘으면 출시한다. (15:09)
  • API는 에이전트 중심으로 설계된다. 클라이언트 도구(bash, 텍스트 에디터 등)와 사고·effort 조절 장치가 에이전트의 성패를 가른다. (16:33)
  • Claude Managed Agents(베타)는 Messages API 위에 만들어져, 에이전트 쪽에서 얻은 교훈이 Messages API에도 그대로 반영된다. (17:46)

기억할 숫자·인용

  • 프롬프트 캐시 적중률 90% = "꿈의 숫자"
  • "모델 지능만큼 중요한 것은 없다."
  • 출시된 기능 하나당 내부 실험 변형이 약 10개

생각해볼 점

  • 캐싱·eval 중심 조언은 Anthropic 입장에서의 권고다. 실제 절감 효과는 내 워크로드로 직접 측정해야 한다.
  • "상위 모델이 결국 더 싸다"는 주장은 영상에서 일반 수치 없이 설명만 나왔다. 작업별로 검증이 필요하다.
  • Mythos/Fable의 접근 구분과 증류 방지 조치는 개발자 경험을 제한할 수 있는데, 구체적 기준은 영상에 나오지 않았다.

바로 해볼 일

  • 내 에이전트 요청이 "덧붙이기" 구조인지 확인하고 프롬프트 캐시 적중률을 측정한다.
  • 쓰는 모델과 effort·thinking 설정으로 작업당 비용·토큰·성공률을 비교하는 eval을 만든다.
  • 새 모델이 나오면 하네스에서 모델이 이제 알아서 하는 부분을 걷어낼 수 있는지 점검한다.
